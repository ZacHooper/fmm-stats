Naming the unknown regions of an FMM27 save

A Football Manager Mobile 2027 save is 70 MB. The parser reads most of it, but twelve stretches between known tables hold about 17.7 MB that nothing reads yet. This plan says what each one probably is, how to find out, and in what order, so anyone can pick up a region without having been part of the work so far.

What you need to know first

How a save is laid out

The file is a run of tables, one after another, always in the same order. The first 27 MB is the game's world database (people, clubs, competitions); after that comes the running career (contracts, transfers, matches, history), and a compressed archive closes the file. Tables are separated by runs of padding bytes, ff or 00.

How a table is usually found

Most tables start with a number saying how many records follow, and every record has the same width. Read the number, step that many records, and you should land exactly on the next table's padding. When you do, the table is found and its end is proved. Some tables instead are fixed grids of empty slots, linked lists, or records whose lengths chain into each other.

What "named" means here

A region is done when its start and end are proved by the bytes themselves, every byte is either a named field or declared unknown, and at least one field is matched to something the game shows on screen. A guess that fits one save is a lead, not a result.

Words used below: a tid is a person's or club's id, which is also its row number in the person or club table. Stride is a record's width in bytes. Live means the bytes change between saves a few days apart; static means they don't.

The loop for every region

Same steps each time. Each step is cheap; skipping one is how a wrong reading gets in.

  1. Profile it. Run scripts/audit/entropy_profile.py over the region. Padding reads under 1.5 bits a byte, records 2–6, text 6–7.5. Skip padded stretches; start where the records are.
  2. Look in front of the first record. A count there that equals a table we know (44,960 people, 36,344 players, 6,212 staff, 9,830 clubs, 1,706 competitions) tells you what the rows are about before you read one.
  3. Prove the width and the end. Find the stride at which columns agree, then check count × stride lands on the next frame. If row k holds k, or holds tid k, check it on every row.
  4. Diff the saves. Compare 22 July, 25 July and 8 August. Which rows changed, and does the change match something that happened in game between those dates (a signing, an injury, a match)?
  5. Match it to a screen. Pick a few rows, find the person or club, open the matching in-game screen and pin what it shows to the bytes in an evidence test (tests/test_*_evidence.py).
  6. Check the other game. Find the same table in an FMM22 Frem save. A reading that holds on one save of one game is a hypothesis. FMM22's extract must stay byte-identical (tests/assert_identical.py).
  7. Hook it up. A parser table with its own locator, then an extract.py step. Update the table doc in docs/parser/, the save map and the TODO.

The 25-byte table contract grid → transfer band · 1.67 MB

LeadStride 25 confirmed. Rows open with a tid and carry two dates a season apart (e.g. day 199 of 2026 and day 150 of 2027). Half the bytes change in two weeks and it grows (+24 KB). Live, career-wide, dated by season.
HypothesesContract offers or clauses, loan deals, scouting assignments, or player promises. Two dates a season apart look like "from / until".
TestResolve the tid on the first hundred rows. If they are players at many clubs, check them against loan lists and scout reports on screen. Find its true start and the row count.

The per-player block transfer band → surnames · 2.41 MB

LeadOpens with 36,344, exactly the player-attributes count. 2.41 MB / 36,344 is ~66 B a player, but no single stride fits, so rows vary like the player-attributes table (a fixed part plus a counted list). Its size held to within 4 KB across saves while half the bytes changed.
HypothesesPer-player match form or season stats (FMM22's match slots sat near here and aren't found on FMM27), or per-player history of the current season.
TestTry "fixed head + u8/u16/u32 count × fixed item", as player attributes was solved. Pick a player who played a match between two saves and diff his row.

Competition record books club records → player progress · 203 KB

LeadCount 176 (FMM22: 162 on every save), variable rows carrying 21-byte match records shaped like the club records' best-win entries. Same size on all three saves.
HypothesesEach competition's record book: biggest win, highest attendance, record scorer. 176 and 162 would be the number of competitions with records.

Lead42-byte rows; the first dates fall after each save (day 207, the day after the 25 July save; day 231, eleven days after 8 August). FMM22 has a 14-byte dated table in the same place, its dates up to a fortnight ahead.

3 the big unknowns · after phases 1–2

Large or mostly empty regions with weak leads

  • The rest of our matches → player lists (5.2 MB). On FMM22 this stretch holds the league-titles table and a player-list block; look for both first. Repeating 72- and 16-byte patterns; about half the bytes change in two weeks.
  • Rule files → contract grid (2.43 MB). Mostly ff with 6-byte ffffffff 01 00 units, but a quarter of the bytes changed in two weeks, so it isn't plain padding. A fixed grid that fills as the career goes on is the likeliest reading; find a filled slot and read its neighbours.
  • Nicknames → history (2.14 MB). 95% zero, but its last ~170 KB holds counts of 3,125 (Truro's own tid) and 10,000. Start from those and read backward.
  • Training → our matches (107–146 KB). 92-byte rows. It shrank by 39 KB while our matches grew, which suggests our-matches' real start, or a table that hands over space to it. Check this before reading the rows.

Done for each when it is either read into a table or proved padding on every save (Phase 4's test).

Rules that keep the readings honest

Never validate a field by joining on it

A check that matches rows on the date and then reports "the dates agree" can't fail. Join on an id or a score and let the field under test come out as the answer.

Prove the end, not just the fields

Fields that match a screen say nothing about the bytes you didn't read. A table is found when the walk lands exactly on the next one, on every save.

No tuned constants

A table bounded by "stop after 50 misses" or a plausibility window returns a short table that looks right. Bound it by its own count or invariant.

Two saves agreeing prove little

A "constant" needs a third save, and a reading on Truro needs the FMM22 Frem saves too. Frem's five seasons of saves are the best test of anything that grows.
