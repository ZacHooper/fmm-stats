Goal

Get extract.py running cleanly end-to-end against the Truro FMM27 saves. Every table should end up in one of three states: confirmed unchanged and reading correctly, re-located and re-declared for the new layout, or explicitly flagged new/removed and parked out of scope. Throughout, the existing FMM22 saves (Frem, Bucaspor) must keep extracting byte-identically — tests/assert_identical.py is the regression gate for that.

What we already know

Rather than guess, I ran the parser directly against both saves before writing this plan.

blocks everything The header format changed completely. extract.py exits immediately: 
the save's header title has no readable date, so the snapshot cannot be placed; is this an FMM22 save?
FMM22's header is a fixed 250-byte NUL-padded string, "<d/m/yy> - <manager> (<nickname>)". A hex dump of the first ~500 bytes of both Truro saves shows something structurally different — not a drifted offset, a different encoding: 
0a00 0000 "Truro City"   (u32 length-prefixed string)
05 00 0000 "Truro"        (another pstring)
05 00 0000 "Truro"        (another pstring)
... binary fields ...
10 00 0000 "27.0.0-d+2495469"      (pstring: build version)
11 00 0000 "fmm27-rel-staging"     (pstring: channel)
0e 00 0000 "27.0.0+2495469"        (pstring: a second version string)
11 00 0000 "fmm27-rel-staging"     (pstring: channel, again)
... more binary fields, including what look like 4-byte timestamp-shaped values ...
This is the same shape as core.primitives.pstring (u32-length-prefixed strings) already used elsewhere in the parser — just not previously used for the header. No plain-text date is visible the way FMM22's was; the field that identifies the snapshot has moved and must be re-found.

Root-cause hypotheses — to test, not conclusions

  1. Header: moved from a fixed 250 B text title to a tagged/length-prefixed record carrying several pstrings (club name, manager name(s), build version, channel) plus binary fields, one of which is presumably the in-game date in a new encoding.
  2. Person/staff records likely grew or reordered (new attributes, roles, or UI data shipped with FM27). Several tables located as "the previous table's end" would break even if their own shape is unchanged, once an upstream table's stride shifts the start address they're searched from.
  3. Career-half tables are "reserved space" — fixed-capacity pools sized when the career was created (docs/parser/savefile-map.md calls this out explicitly for contracts, player progress, match slots, player lists). A new game version plausibly resized these pools or widened their row shape, breaking the id == slot index / stride invariants the current walks assert.
  4. The archive's directory format changed independently of the rest — a different footer, compressor settings, or member-record width.

Phase 1 — decode the new header

Doesn't unblock any table structurally, but unblocks running extract.py at all, and recovers the one field every snapshot is identified by: the date.

  • Done: walked the header as alternating pstrings/u32s up to offset 0x100 — club name, three repeats of build version + channel, five small counts, then a run of timestamp-shaped 4-byte values starting at 0x100 that isn't yet matched to anything (see the finding above).
  • Next, find the date by its known encoding first. The parser already has a 4-byte DATE type (fmparser/core/types.py). Decode every 4-byte offset from 0x20 to ~0x200 as a DATE and list the plausible ones. The right field reads as the 22nd in save_2 and the 25th in save_1.
  • Then confirm by diffing. Diff save_1 against save_2 byte-for-byte over the same range. They're the same career three in-game days apart, so the date field must be among the bytes that change, and build metadata must not.
  • Version detection, minimal for now: FMM22 starts with ASCII d/m/yy text and FMM27 starts with a u32 length followed by the club name. That's enough to tell these two apart, so the header reader dispatches on it.
  • Open a TODO for deterministic version identification. The shape check above can't tell FMM26 from FMM27, because both probably use the pstring header. The real answer is to read the version the save declares about itself: the build string (27.0.0+…) or the 27,000,034 u32 at 0xaf, which looks like an encoded version number. Then map it to a declared format. Not needed to ship FMM27 support; needed before a third version.
  • Decode it as a sequence of pstrings followed by binary fields, using the existing core.primitives/core.types readers — no new primitive should be needed, just a new Record declaration.
  • Add a new header reader that returns the same shape extract.py already expects ({title, date, manager, nickname}), so nothing downstream has to change.
  • Pin the date against ground truth: the continue-game date shown in the FM27 client for these saves.

    • an on screen → raw bytes → parsed table for the rows the screenshot shows;
    • an evidence test (tests/test_*_evidence.py) pinning the bytes as well as the parsed value;
    • the plan's Learnings section and the TODO entry updated, leads promoted to confirmed or dropped.
    A table isn't "done" until its doc is. That makes Phase 7 a check rather than a write-up.
"found" ≠ "correct" The tables that still locate are only located, not yet confirmed as reading correctly. Row counts are rough checks. FM27 could keep a stride but reorder or repurpose fields (player_attributes is the obvious risk). Because every declared record reads every byte, a mislabelled field still shows up in the output as a value that's wrong. So each one is checked by comparing a few rows against an in-game screen: one player's attribute page, one city, one name. Only then does it move to confirmed unchanged.

Phase 4 — the archive

  • Re-derive core/archive.py's directory parsing independently of the rest of the file. The error (frame at 69,331,477 declares 50,331,648 bytes, past EOF) means the current directory-offset math is reading a wrong length or wrong offset — check whether the directory itself moved, or whether its per-member record (name/offset/length) changed width.
  • Clue: 50,331,648 is exactly 48 MiB (0x3000000). A round number like that is more likely a capacity or decompressed-size field being read as a frame length than random bytes. Check the zstd frame header's own content-size field and the member record width first.

Phase 5 — new sections, not just moved ones

  • Once every currently-known table re-locates, run audit_coverage.py over the whole file to find bytes no table claims, and compare against the old savefile-map's "UNIDENTIFIED" spans.
  • Some of those gaps may now be explained by genuinely new FM27 features rather than a moved old table — those need their own new table definitions, not a forced fit into an existing one.

Phase 6 — version dispatch design needs a decision

The parser currently has no concept of a game-client version — only career-agnosticism. We need to decide how it tells an FMM22 save from an FMM27 save and picks the right table declarations for each, without blurring the existing "parser is career-agnostic" boundary rule (version is a different axis to career, but still needs a named concept passed down rather than guessed per table). Identification is done: save_format() reads the declared fmm<NN>, defaulting to FMM22. What's left is how a table picks its declaration (locator + records) from that value, decided once the first broken table is re-declared.

Phase 7 — regression + documentation

  • Check, don't write: every table doc should already have its FMM27 layout and evidence from Phase 3. Sweep for any that don't, and update savefile-map.md with an FMM27 column or companion map.
  • Re-run tests/assert_identical.py on the FMM22 saves to prove zero regression; add the Truro saves as new fixtures once the extract is stable.
  • Delete the TODO entry from Phase 0 once this closes, per the project's own rule.
