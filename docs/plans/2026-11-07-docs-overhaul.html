Why

The docs grew with the project: 80 files, ~14,500 lines of current reference, finished plans, vendored assistant memory and investigation logs. A scan on 2026-11-06 found ~95 references to files that no longer exist, across 37 docs. A stale doc is worse than none, because it reads as authoritative. Fewer docs is better, as long as nothing true and hard-won is lost.

Who reads them:

  1. Now: developers using this code to improve their own parsers and tools.
  2. Later: players who don't code. Their agent clones the repo, they hand over a save from their phone, and they're done.

So the README and each part's overview are written for people, and the README opens with the fastest possible start. Everything else is written for agents, and kept lean: a dense doc wastes an agent's context as much as a person's attention.

Rules for every phase

  1. Describe the present. The parse is deterministic now; say how it works today. How we got here stays in git history. No "we used to", "until now", "it turned out".
  2. Keep a nugget only if it is still true (checked against the code or the data) and it prevents a wrong answer or would take real effort to rediscover. Narration, status updates, step logs and superseded hypotheses go.
  3. Decisions, dead ends and quirks are callouts in the doc about the thing, never a separate file and never comment clutter in code (see the framework).
  4. Harvest, write, delete, in one PR. Pull the nuggets out of the docs you retire, write them into their new home, delete the old doc, fix every link. Link the old doc's last commit in the PR description, so the full story stays reachable.
  5. Verify, don't copy. Every claim moving into a new doc is checked against the current code or a store. A claim you can't check is dropped or marked as unverified.
  6. Lean. Link to detail instead of inlining it. One doc, one reader, one job.
  7. No data in git: no saves, stores, extracts or exported JSON. In-game screenshots as evidence are fine (docs/parser/img/, cropped, small).
  8. No career-specific facts in public docs. Frem is a worked example at most; what is only true of one career goes to the author's CAREER.md.
  9. Cite TODO entries by title, never by number: numbers are reused.
  10. Green before you push: tests/run_tests.py, tests/test_boundary.py, the docs checker once it exists, and for any fmstats/ change a load that passes.

Evidence

Mostly a parser concern, and the weakest part of the docs today. Each table gets at least one ground-truth record: an in-game screenshot, the value it shows, the raw bytes, and the parsed value. Screenshots go in docs/parser/img/<table>-<n>.png, cropped to the panel that matters. Where it can, the record is also a test fixture in tests/fixtures/ that asserts the parse.

Column definitions (stats)

Every column concept is defined once, as a dbt doc block in fmstats/models/_docs/ (one file per family: ids.md, time.md, match_stats.md, money.md, player.md, …), and every model's yml points at it.

{% docs appearances %}
Appearances: matches the player took the field in, as starter or substitute.
{% enddocs %}
columns:
  - name: appearances
    description: '{{ doc("appearances") }}'
  - name: from_club_tid          # a role on a shared concept: one sentence, then the block
    description: 'The club he left. {{ doc("club_tid") }}'
  • Coverage: every mart and site column. In stg and int, only where a name carries through to the upper layers.
  • The block is named after the canonical column name, so the lookup is mechanical.
  • The drift audit, scripts/check_dbt_docs.py, reads target/manifest.json (dbt parse needs no store, so it runs in CI) and fails when a mart/site column has no doc(), a doc() names a missing block, a block is unused, two same-named columns use different blocks, or a column breaks the naming convention or uses a listed synonym.

Column naming convention

When two names compete, these decide it, in order:

  1. The game's own word wins. If the game's screens name it, use that word: appearances, not apps, matches_played or n_games.
  2. Whole words, no abbreviations: opponent_tid, not opp_tid. Established ids stay (tid, cid).
  3. One name per concept across the warehouse. A role on a shared concept is a prefix: <role>_<concept> (from_club_tid, home_team_tid).
  4. Relative to the row's subject: goals_for / goals_against, or home_ / away_. Never _a / _b.

Drift visible today in mart and site (models using each name): apps[4], matches_played, n_games, played, appeared; opponent_tid[4] vs opp_tid; value[4], value_gbp, value_now; fee_kind[4] vs fee_type; goals_for/goals_against vs goals_a/goals_b. Some may be different concepts (a flag, not a count): writing the block decides it.

Phases

One PR per phase (or per table group in phase 2). Each brief stands alone.

0. Docs checker

Goal
Docs can't silently go stale again: a broken reference fails CI.
Read first
AGENTS.md, .github/workflows/ci.yml.
Do
  • Write scripts/check_docs.py: in every .md and .html doc, each repo path it cites (fmparser/…, scripts/…, tests/…, fmstats/…, site/…, docs/…) must exist, and each relative link must resolve, anchors included.
  • Exit non-zero with a list of file:line → missing target.
  • An allowlist for paths that are deliberately absent (gitignored outputs such as site/api/, fmm.toml, CAREER.md).
  • Run its first pass and commit the output as the work list in this file's map; add it to CI as a non-blocking step until phase 7, then make it blocking.
Don't
Fix the docs it flags; that's the later phases' job.
Done when
The script runs in CI and its report is attached to the PR.

2. Parser: one doc per table

Goal

Read first
fmparser/AGENTS.md, docs/parser/savefile-map.md, the table's module.
Split
One PR per group, so several agents can work at once:
  • people: person_info, player_attributes, player_progress, player_lists, names, history, contracts, training, staff
  • matches: matches, match_slots, fixtures, rounds, officials
  • competitions: competitions, comp_stages, comp_rules, comp_honours, rule_files
  • world: clubs, club_records, nations, cities, stadiums, currencies, languages, save_header
Do
  • Write docs/parser/<table>.md from the module's docstring and the current code; harvest from the source docs in the map.
  • Evidence: name the in-game screen to capture, ask the author for the screenshot, map the value on screen to the raw bytes and the parsed field. Add a fixture test where it can be made small.
  • Fold BUGS.md items for these tables in as Dead end / Quirk callouts.
  • Move the whole-file map to docs/parser/savefile-map.md, linking each table to its doc.
  • Last group: write fmparser/README.md and trim fmparser/AGENTS.md to the method and the feedback loop.
Done when
Each table in the group has its doc and an evidence record; retired source docs are deleted in the same PR.

Do

Why not rewrite this one
GitHub keeps every merged PR's commits reachable through refs/pull/*, which a rewrite can't remove, and 47 of the 81 branches carry an older unrelated history.
